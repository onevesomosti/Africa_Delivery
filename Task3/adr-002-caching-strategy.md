# ADR-002: Стратегия кеширования

Дата: 13.10.2026 
Статус: Предложено, требует согласования CTO

## Контекст
Приложение должно обеспечивать быструю работу каталога товаров даже при нестабильном мобильном интернете.

Основные требования и ограничения:
- Более 60% трафика приходится на мобильные устройства с подключением через 3G/4G. Соединение может быть медленным и нестабильным.
- Первый товар должен появляться на экране покупателя менее чем за 2 секунды.
- В рамках MVP каталог должен поддерживать 5000 SKU от 100 продавцов.
- Ежемесячные расходы на облачную инфраструктуру ограничены $5000.
- Для MVP выбрана архитектура модульного монолита с возможностью последующего масштабирования.

Для выполнения этих требований необходимо сократить количество обращений к основной базе данных и объём информации, передаваемой через мобильную сеть. При этом кеширование не должно приводить к оформлению заказов с неактуальными ценами или остатками товаров.

Источники: описание кейса, артефакт 2, артефакт 6, п. 1, FMEA F-01 и F-07.

## Рассмотренные варианты

| Вариант | Преимущества | Недостатки |
| --- | --- | --- |
| Без кеширования | Простая реализация. Данные запрашиваются непосредственно из основной БД | Высокая нагрузка на БД. Повторная загрузка одних и тех же данных увеличивает время ответа и расходует мобильный трафик |
| Серверное кеширование (Cache Aside) | Часто запрашиваемые данные сохраняются в кеше и не требуют повторного обращения к БД | Требует дополнительной логики обновления кеша. При использовании Redis увеличиваются расходы на инфраструктуру |
| Клиентское кеширование и CDN | Изображения и другие данные загружаются быстрее, уменьшается расход мобильного трафика | Пользователь может видеть устаревшую информацию, если кеш не обновляется вовремя |

## Решение

Для MVP предлагается использовать многоуровневое кеширование данных, которые часто запрашиваются и не требуют постоянного обновления.

Кеширование реализуется на трёх уровнях:
1. Мобильное приложение. Повторно использует ранее загруженные изображения и часть данных каталога. Это уменьшает расход трафика и позволяет быстрее открывать уже просмотренные страницы.
2. CDN (Content Delivery Network). Хранит копии изображений товаров ближе к пользователям, сокращая время загрузки.
3. Серверное кеширование. Сохраняет часто запрашиваемые данные каталога, чтобы уменьшить нагрузку на основную БД.

Для серверного кеширования предлагается использовать паттерн Cache Aside. Redis рассматривается как возможная технология, но не является обязательным компонентом MVP.

Источник — артефакт 2, артефакт 6, FMEA F-01.

### Правила кеширования

| Данные | Где кешируются | TTL | Как обновляются |
| --- | --- | --- | --- |
| Изображения товаров | CDN, мобильное приложение | 24 часа | При изменении изображения создаётся новый URL, чтобы приложение загрузило новую версию |
| Категории товаров | Мобильное приложение, сервер | 1 час | Кеш очищается при изменении справочника категорий |
| Карточка товара без актуальных остатков | Мобильное приложение, сервер | 5 минут | Кеш очищается при изменении информации о товаре |
| Результаты поиска товаров | Сервер | 1 минута | Данные обновляются после истечения TTL или при изменении поискового индекса |
| Настройки интерфейса | Мобильное приложение | 1 час | При изменении настроек обновляется версия конфигурации |
| Цена и остатки перед оформлением заказа | Не используются из кеша как окончательные данные | — | Перед подтверждением заказа система проверяет актуальную цену и наличие товара в основной БД |
| Статус платежа | Не используется из кеша для принятия финансовых решений | — | Актуальный статус определяется по сохранённому состоянию операции и подтверждениям платёжного провайдера |

Значения TTL являются предварительными и должны быть проверены при тестировании.

### Данные, для которых кеширование ограничено

Не все данные подходят для кеширования. Особое внимание необходимо уделить следующим операциям:
- Оформление заказа. Перед подтверждением покупки система должна проверить актуальную цену и остаток товара в основной БД.
- Оплата. Решение об успешности платежа принимается только на основании подтверждённого состояния операции.
- Изменение данных продавцом. При изменении карточки товара соответствующая информация в кеше должна обновляться или удаляться.

Это необходимо для предотвращения ошибок, связанных с устаревшими данными.

Источник — FMEA F-07, артефакт 4.

## Последствия решения

### Положительные
- Быстрее работает каталог. Часто запрашиваемые данные загружаются из кеша без повторного обращения к БД.
- Снижается нагрузка на БД. Уменьшается количество одинаковых запросов.
- Сокращается мобильный трафик. Изображения и ранее загруженные данные не требуется скачивать повторно.
- Повышается устойчивость к нестабильному соединению. Часть ранее полученного содержимого остаётся доступной в мобильном приложении.

### Отрицательные
- Риск устаревших данных. Покупатель может увидеть информацию, которая уже изменилась в основной БД.
- Усложнение разработки. Необходимо реализовать TTL и механизм инвалидации кеша.
- Дополнительные расходы. Отдельный серверный кеш, например Redis, увеличивает стоимость инфраструктуры.
- Усложнение диагностики. При ошибках необходимо проверять не только БД, но и актуальность кешированных данных.

Источник — FMEA F-01 и F-07, артефакт 6.

## Отложенные решения

| Решение | Условие принятия | Источник |
| --- | --- | --- |
| Использование Redis | Нагрузочное тестирование покажет, что без отдельного серверного кеша не выполняются требования к времени ответа | Арт. 2, 6, FMEA F-01 |
| Увеличение объёма серверного кеша | Фактическая нагрузка на каталог потребует дополнительного сокращения обращений к БД | FMEA F-01 |
| Изменение TTL | Тестирование или эксплуатация выявит устаревшие данные либо избыточную нагрузку на БД | FMEA F-07 |
| Расширение клиентского кеширования | Появятся подтверждённые требования к работе приложения без интернет-соединения | Арт. 2, описание кейса |

## Триггеры пересмотра

ADR необходимо пересмотреть, если:
1. P99 каталога превышает установленное целевое значение в 1 секунду.
2. Основная БД не справляется с нагрузкой на чтение.
3. Покупатели регулярно получают устаревшие данные о товарах.
4. Из-за кеширования возникают ошибки при оформлении заказов.
5. Стоимость инфраструктуры превышает бюджет CFO.
6. Возникают новые требования к работе приложения при отсутствии интернета.

Источник — артефакты 2 и 6, NFR-05, FMEA F-01 и F-07.

## Допущения
1. Актуальность каталога. Предполагается, что ограниченная задержка обновления описаний товаров и категорий допустима. Точные требования к актуальности необходимо согласовать с бизнесом.
2. Значения TTL. Указанные интервалы выбраны как начальные настройки и должны быть проверены на реальной нагрузке.
3. Клиентское кеширование. Предполагается, что мобильное приложение поддерживает хранение ранее загруженных данных. Полноценная работа без интернета не входит в утверждённый объём MVP.
4. Возможность использования CDN зависит от выбора инфраструктуры и требований к размещению данных.
5. Серверное кеширование. Redis не включается в обязательный состав инфраструктуры до подтверждения его необходимости нагрузочным тестированием и расчётом стоимости.
