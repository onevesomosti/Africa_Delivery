# ADR-003: Стратегия размещения данных

Дата: 13.10.2026 

Статус: Предложено, ожидает согласования CTO, CFO и юридического консультанта

## Контекст

Необходимо запустить MVP в Нигерии и Кении 15 октября 2026 года.

Юридический консультант предварительно указывает на требования локализации данных и ограничения трансграничной передачи. Окончательные условия обещаны через четыре–шесть недель.

При этом облачная инфраструктура ограничена бюджетом $5000 в месяц, а архитектура должна допускать перенос к другому провайдеру.

Источники: артефакт 1, артефакт 3, п. 1–3, артефакт 6, п. 1

## Рассмотренные варианты

| Вариант | Преимущества | Недостатки |
| --- | --- | --- |
| A. Единый контур в ЮАР | Простое управление, доступные облачные сервисы | Не соответствует консервативной политике локализации Нигерии и Кении |
| B. Отдельные национальные контуры  | Персональные данные остаются внутри страны, можно менять правила каждой страны независимо | Дополнительные расходы, более сложная эксплуатация |
| C. Гибридная модель с токенизацией | Локальное хранение персональных данных, возможность централизованной обработки разрешённых данных | Необходима проверка статуса токенов и допустимости трансграничной обработки |

## Решение

Выбран вариант B с возможностью перехода к варианту C после юридического подтверждения.

1. Для каждой страны используется отдельный контур хранения и обработки персональных данных.
2. Бизнес-логика остаётся общей по кодовой базе модульного монолита, но развёртывается с отдельной региональной конфигурацией.
3. Регион определяется по стране обслуживаемого субъекта, а не только по IP-адресу пользователя.
4. Платёжные и логистические интеграции подключаются через отдельные адаптеры.
5. Централизованная аналитика получает только проверенные обезличенные агрегаты.
6. Все межрегиональные передачи проходят через отдельный контролируемый интерфейс.

Источники: артефакт 3, ADR № 1, NFR-16, NFR-18.

## Защита персональных данных

| Механизм | Решение | Источник |
| --- | --- | --- |
| Маскирование | Скрывать телефон, адрес и другие персональные поля в логах и интерфейсах без соответствующих прав | `observability.md`, раздел «Логи» |
| Шифрование | Шифровать данные при передаче и хранении | Арт. 3, NFR-17, NFR-18 |
| Управление ключами | Отдельные ключи для каждого национального контура, доступ только уполномоченным компонентам | NFR-17 |
| Токенизация | Использовать случайные идентификаторы вместо персональных данных в межсистемных взаимодействиях | Арт. 3, п. 1|
| Репликация | Размещать основную и синхронную резервную БД на независимых площадках внутри соответствующей страны. Перед failover исключать запись на старой площадке | Арт. 3, NFR-18, QAS-05, FMEA F-02 |
| Резервное копирование | Хранить зашифрованные резервные копии на независимой площадке в той же стране | FMEA F-02, NFR-18 |
| Сроки хранения | Настраивать по категории данных, без жёсткого закрепления в бизнес-логике | Арт. 3 |
| Удаление | Поддерживать удаление или обезличивание после истечения установленного срока | Арт. 3 |

Шифрование и маскирование защищают данные, но не отменяют требований к месту их хранения. Токенизация также не считается автоматическим разрешением на зарубежную передачу.

## Обратимость решения

| Что может уточниться | Как адаптируем систему без переписывания |
| --- | --- |
| Разрешена передача отдельных категорий данных | Обновляем правила передачи, открываем только согласованные потоки |
| Псевдонимизированные данные признаются персональными | Оставляем их внутри национального контура, запрещаем экспорт |
| Разрешена централизованная обработка обезличенных данных | Подключаем региональный экспорт агрегатов |
| Уточняются сроки хранения | Меняем политики жизненного цикла данных через конфигурацию |
| Необходимо сменить провайдера | Развёртываем тот же контейнер приложения, переносим БД и ключи по утверждённому плану |
| Ужесточаются требования локализации | Отключаем соответствующие межрегиональные потоки без изменения модулей заказов и оплаты |

Для обеспечения обратимости правила размещения, сроки хранения и разрешения на передачу не должны быть жёстко зашиты в бизнес-код.

Инфраструктура описывается декларативно, изменения проходят через CI/CD. Региональные особенности изолируются на уровне конфигурации и адаптеров.

Источники: NFR-15, NFR-16, ADR № 1, CN.ADL.04.

## Последствия

Положительные: снижается риск нарушения предварительных требований локализации, сохраняется переносимость, юридические уточнения не требуют переработки всей платформы.

Отрицательные: возрастают расходы на отдельные контуры, мониторинг и резервирование. Сквозная аналитика ограничена. Необходима проверка возможностей локальных провайдеров.

## Триггеры пересмотра

ADR пересматривается при получении юридического заключения, изменении законодательства, отсутствии подходящего локального провайдера, превышении бюджета CFO или обнаружении недопустимой трансграничной передачи.

## Допущения
1. Сроки хранения, правила удаления и конкретные технологии управления ключами утверждаются после юридического и технического согласования.
2. Выбранная архитектура описывает целевое развёртывание MVP, но фактическая готовность площадок и финансирование пока не подтверждены.
3. Наличие двух независимых площадок и синхронной репликации в каждой стране требует подтверждения провайдерами, расчёта стоимости и отказных испытаний для проверки RTO 30 минут и RPO 0.
